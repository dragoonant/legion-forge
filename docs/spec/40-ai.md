# 40 - AI opponent

The AI is the opponent of the solo game: an army that picks command cards for a reason, activates the right unit at the right time, moves to cover and objectives along the movement tool, attacks where the odds pay, spends aim and dodge, and never wastes an activation. One `Decider` per tier in `src/ai/`, running in a Web Worker in the client (`src/ai/worker.ts`) or inline (bench, tests, sim). Method carried over from Mancermundo (`legacy/src/ai/`): per-activation utility scoring, threat map, worker with fallback, tiers, bench as a rules fuzzer. The rules underneath are Legion's.

## 1. What it may see and use

- Input is only `view(state, seat)`, `pending`, and `legalActions(state, pending, seat)` (finite) or `validate` (continuous). It never sees the opponent's unrevealed command pick, the order of any order pool, the RNG or the log (`00-architecture.md` 3.2). Tests feed it a redacted view and assert it never touches hidden fields.
- Every number comes from the engine: `query.attackOdds`, `attackTargets`, `losCover`, `toolPreview`, `rallyOdds`, `panicOdds`, `cohesion`, `battleView`, `pending.options[].data`. The AI composes them; it never re-derives a die face, a range band or a cover verdict.
- Answers only from `pending.options` or a continuous action that passes `validate`.

## 2. Tiers and entry points

| Tier | Behaviour |
|---|---|
| `random` | uniform over action types first, then over options; tool placements and deploy spots are random legal samples. Bench baseline and sim bot. |
| `easy` | the same scoring with noise (random pick among the best three within 0.6 of the best), fewer tool samples, a weaker threat map, no action-pair lookahead, objectives at half weight. |
| `normal` | full scoring: action pairs, full tool sampling, threat map, objectives, command-card policy, standby and aim/dodge planning. |

`src/ai/index.ts`: `createAiDecider(tier, { seed, budgetMs?, weights? })` (implements `Decider`; `decideSync(view, pending, legal)` returns `{ action, fallback, ms }`), `createAiBot(tier, seed)` (drop-in for the client's random bot), `AiWorkerClient` (posts each decision to the worker; answers in-process with the same code when there is no `Worker`, the worker errors, or **3 s** pass). Randomness: `SeededRng(seed | decision id | tier)`. `AI_TUNE` overrides weights, `AI_TRACE=1` prints scored candidates (node).

## 4. Scoring model

Everything is in points (the unit's points cost from data). **Every candidate is scored against the do-nothing baseline at the same horizon:** the value of the board after the candidate minus the value of the board if the unit did nothing, both evaluated at the end of this activation with the same threat map. "End activation" scores exactly 0; anything else must beat it.

- **Threat map.** For a unit at a spot: expected wounds and suppression it would take from each enemy unit that can still act this round (face-up order 1.0, in the pool by rank probability, already activated 0.3 for standby and next round), using `query.attackOdds` with the cover `losCover` reports from that spot. Panic risk adds `pPanic x unit value x 0.5`.
- **Position value.** `-threat + objective progress + support (courage source, cohesion with friends in range) - distance to goal (damped while an attack is in hand)`.
- **Attacks.** `expectedWounds x value per wound + suppression value + pDefeat x remaining value`, minus friendly risk (e.g. a charge's exposure), from `query.attackOdds` with the chosen weapons and every spend option the engine offers.
- **Aim, dodge, standby, recover.** Aim = gain in the following attack's expected value; dodge = threat reduction at the end spot; standby = `P(trigger) x value of the response` from the threat map's approaching enemies; recover = suppression and exhausted-card value removed. Each is valued only through the attack or threat it changes.
- **Objectives.** `battleView` gives each objective's value to each seat and the victory projection; claim, contest and hold moves score their projected points delta.
- **Stall breaker.** After a round with no wound and no point scored, the objective and approach pulls grow by about 25% per quiet round.

## 5. Activation planner

1. **Which unit / which order.** For each unit with a face-up order and for the pool draw (expected value over the ranks remaining in the seat's own pool, which the seat knows), score the best plan the unit can make now. Prefer spending orders on units whose plan is time-sensitive (an attack that may vanish, an objective about to be contested); keep a pool draw when the remaining pool units all have similar value.
2. **Move end points.** Sample the movement tool: each offered speed x hinge angles (a fixed grid, finer for `normal`) x lengths along the tool; drop samples `toolPreview` rejects; keep the best N by position value; troopers placed by `suggest` unless a placement improves cover.
3. **Action pairs.** Enumerate the pairs the ledger allows (move+attack, aim+attack, move+move, attack+move, move+dodge, move+standby, recover+move, card or keyword actions), score the pair's end state against the baseline, then answer the first action. Free actions are scored when offered.
4. **Command cards.** `value(card) = orderValue(card) + effectValue(card) + P(priority | card) x priorityValue`. `orderValue` = sum over the units it can order of (value with a face-up order - value from the pool); `P(priority)` assumes the opponent picks uniformly among its remaining cards (open information), with the tie roll-off at 0.5; `priorityValue` grows when an objective or a decisive attack depends on activating first. Cards the AI cannot use well this round are kept for later rounds (one-use value carried over).

## 6. Never random, always counted

A missing policy, `null`, an illegal answer or a throw is answered by `suggestPolicy` (engine `suggest`, else the first non-pass option, else pass), never a random action for `easy`/`normal`. Counted in `stats`: `fallbacks` (per kind), `unhandled`, `errors`, `hardStops`, `workerTimeouts`.

**Behaviour counters from day one** (bench report, per tier): zero-action activations (ended with an action on offer), aim tokens never spent, dodge tokens never spent, standby tokens that expired untriggered, objective interactions (claims, contests, points scored per game), orders issued vs pool draws, command cards by round.

## 7. Bench (`npm run bench:ai`)

`npm run bench:ai -- --games 40 [--seed 1] [--tier normal] [--vs random|easy|normal] [--matchup mirror|main] [--holdout]`. The tested tier plays both seats in turn; matchups are fixed: an Empire mirror and the main matchup (Empire vs Rebels), alternating factions; battle cards rotate through the slice; holdout seeds (`--holdout`) are never used while tuning. Only decisive results count toward win rates; a game that hits the round limit is reported separately.

| Gate | Target |
|---|---|
| normal vs random | >= 95% decisive wins, both seats, both matchups, on holdout seeds |
| normal vs easy | normal wins at least as many as easy |
| rejections, stalls, fallbacks, unhandled kinds, errors | 0 |
| zero-action activations | < 2% of activations |
| mean decision time | < 50 ms (p50 also reported; worker hard stop 3 s) |

Report in `tools/out/bench-report.json`: wins by seat, matchup and battle card, the behaviour counters, decision kinds seen, timing per kind.

## 8. Non-goals (v1)

No multi-round lookahead, no opponent modelling beyond the uniform card prior, no bluffing with command cards; a `hard` tier plugs into the planner's lookahead switch later.
